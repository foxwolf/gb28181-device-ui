## 1. 目录应答与心跳：Catalog / Keepalive 改为国标子元素 XML

### 现象

设备已注册在线（示例通道曾显示 contact 可达），但对接的现场网关侧报「目录未见」。REGISTER 成功后，平台发起的 Catalog Query 得不到可识别的目录应答。

### 根因

本程序原先用带属性的 XML 生成 Catalog 应答和 Keepalive 通知，例如 `<Response CmdType="Catalog" ...>`、属性形式的 `<Notify ...>`。部分现场平台（包括本次联调的网关）用字面量子串匹配识别报文，要求正文同时出现：

- 目录应答：`<CmdType>Catalog</CmdType>` 以及 `<Response>`
- 心跳：`<Notify>`、`<CmdType>Keepalive</CmdType>`、`<DeviceID>`、`<Status>`

属性格式无法被这类检测识别，平台就认为没有目录、也无法按心跳刷新在线状态。

这与更早已经合入的「REGISTER 等待期间 `socketResponseSource` 吞掉 Catalog Query」不是同一问题。本次是**发出去的 XML 形态不被平台识别**。

### 证据

2026-11-23 22:56:30，网关日志将 Catalog `sn=2` 记为「目录应答」，从查询到识别间隔约 31 ms，正文为子元素格式。该次会话在 22:57:13 已注销，早于配置的 60 秒心跳周期，**当时没有在同一网关会话上确认心跳**；后续对接 WVP 的注册与在线维持是成功的，但不能把那一次网关心跳写成已经实测通过。

### 代码改动

- `third_party/gb28181-go/device/manscdp.go`
  - 新增 `catalogResponseBody`，以 `xml:"Response"` / `xml:"CmdType"` 等子元素标签序列化。
  - `BuildCatalogResponseMessage` / `BuildCatalogResponseMessagePaged` 改为使用该结构，不再走属性型 `Response`。
  - `BuildKeepaliveMessage` 改为使用已有的 `NotifyElem`，而不再用属性型 `Notify`。
  - `BuildDeviceInfoResponseMessage`、`BuildDeviceStatusResponseMessage` 仍保持属性格式，本次未改。若后续平台对这两类查询也做同样的子串匹配，需要再评估。
- 测试同步更新：
  - `manscdp_test.go`、`backfill_test.go`、`early_request_test.go`、`gb2011_compat_test.go`：断言改为检查子元素标签，而不是属性形式。
  - 新增 `catalog_platform_compat_test.go`：用与现场网关相同的子串条件检查 Catalog / Keepalive。
  - `internal/runner/signaling_test.go` 新增 `TestRunner_CatalogQuery_GatewayWireFormat`，覆盖从 Runner 发出的 Catalog 应答线路格式。

### 机制

SIP MESSAGE 的 MANSCDP 正文改为子元素树后，平台的 `strstr` 类检测可以命中 `CmdType` 与根元素，从而把应答记入目录、把 Notify 记入心跳。不改变 Catalog 分页字段（`SumNum` / `DeviceList Num`）的语义。

## 2. 日志滚动条与「清除日志」

### 现象

用户反馈日志区「显示不是很合理，没有滚动条」，并希望增加清除日志功能。日志本身可以滚轮翻动，但没有可见的垂直滚动条，也没有一键清空。

### 根因

日志列表原先用 Gio 的 `layout.List`，支持滚动但不绘制占用条。新日志追加时，若没有「仅在已位于底部时跟随」的策略，查看历史时容易被拉回底部。

### 证据

属界面能力缺失，不以平台信令日志为判据。修改后由用户在实机窗口中使用（后续粘贴日志、点播排障均在该界面完成）。本次提交前，界面测试仅在 WSL 中交叉编译为 Windows 测试二进制，**没有在 Windows 上运行该测试包，也不得写成「UI 测试运行通过」**。

### 代码改动

- `internal/logview/handler.go`：`Buffer.Clear()` 在锁保护下清空环形缓冲（上限仍为 2000 行），保留会话并通知 `onChange`。
- `internal/ui/ui.go`：日志标题栏增加「清除日志」按钮（`clearLogsBtn`）。
- `internal/ui/logsel.go`：
  - 使用 `material.List` 的 `Occupy`（约 8 dp）绘制可见垂直滚动条；内容未超出显示区时不占用该条。
  - `stickBottom`：仅当滚动位置已在底部时，新日志才跟随到底；用户上翻查看历史时不跳回。
  - 文本命中区域避开滚动条，避免划选与拖条冲突。
  - `clearLogs()` 清空缓冲并重置选择与滚动位置。
- 测试：`internal/logview/handler_clear_test.go`、`internal/ui/logclear_test.go`。

### 机制

日志仍是有界环形缓冲；清除只影响界面缓冲，不影响 SIP 状态。滚动条是官方 Gio List 装饰，不是自绘控件。

## 3. 媒体 TCP 永久写失败后结束会话

### 现象

点播过程中，媒体 TCP 被对端断开后，界面在数秒内刷满同一条 WARN，例如：

`failed to send RTP frame ... write tcp 127.0.0.1:…->127.0.0.1:…: wsasend: An established connection was aborted by the software in your host machine`

直到收到平台 BYE 才停止。连接失效后仍按帧重试写入。

### 根因（分两层）

**设备侧循环缺陷：** 直播发送循环在 `SendFrame` 失败后只打日志，不结束媒体会话，于是每一帧都再失败一次。

**当时点播失败的平台原因（不是本仓库代码）：** ZLMediaKit 已收到并识别 PS 首包，但 `on_publish` 回调里的 `mediaServerId` 与 WVP 配置的媒体服务器标识不一致，WVP 拒绝推流并关闭 TCP。详见第 5 节。不能把这条 Windows 写错误直接归因于防火墙。

### 证据

- 修复前：2026-11-23 23:43:08 起同一 WARN 连续刷屏，至 23:43:10 才收到 `192.168.1.50:50060` 的 BYE。
- 修复后替换程序再测：2026-11-24 00:08:47 收到 INVITE，00:08:48 仅一条 `media TCP send failed permanently, stopping media session`（对端 `forcibly closed`），之后不再刷屏，00:08:57 收到 BYE 并回 200。刷屏问题已消除；该次点播仍因第 5 节的标识不匹配而失败。

### 代码改动

- 新增 `third_party/gb28181-go/device/media_send_error.go`：
  - `isUnrecoverableMediaSendError(err, overTCP)`：将 `ECONNRESET` / `EPIPE` / `net.ErrClosed` 以及 Windows WSA 10053/10054/10057/10058，或报文中的 aborted / reset / forcibly closed / broken pipe 等视为不可恢复。
  - **TCP** 上上述错误会结束本路媒体；**UDP** 只在本地 socket 已关闭时结束。UDP 对「对端不可达」通常不在 `WriteToUDP` 上返回错误，一次发送失败不能当成会话死亡。
  - `(*Server).stopCurrentMediaIf(tcpConn)`：仅当传入的 TCP 连接仍是当前媒体连接时才 `teardownMediaLocked()`，避免与新的 INVITE / 已执行的 BYE 竞态，误拆新会话。
- `third_party/gb28181-go/device/server.go` 直播 `SendFrame` 分支：若 `tcpConn != nil` 且错误不可恢复，打一条永久失败 WARN，调用 `stopCurrentMediaIf` 后 `return`。回放路径本身已在发送失败时退出，未改。
- 新增 `media_send_failure_test.go`：错误分类（含 WSA 与文本匹配）、假 TCP 关闭后不再刷屏、与 BYE 的竞态、重新 INVITE 可恢复、UDP 对端关闭不结束会话。

### 机制

不可恢复的 TCP 写失败视为媒体传输已死，立即拆除当前会话并停止发帧。BYE 到达时拆除是幂等的。这不修复对端为何断开，只消除无效重试和日志洪水。

## 4. 多 slice Annex-B 合帧（WVP 画面马赛克）

### 现象

在完成第 5 节的现场标识对齐后，用户于 2026-11-24 06:17 确认「能看见了，但在 wvp 平台播放的视频有马赛克」，并询问是否「码流太大」。

### 实测码率（排除「码流太大 / 带宽不够」）

对 WVP 在 06:15:22–06:16:43 自动留下的点播录像做只读分析（私有样本，不入库）。路径为平台本机 TCP（INVITE 收流地址 `127.0.0.1`），不是广域网带宽问题。

| 项 | 实测值 |
| --- | --- |
| 容器时长 / 体积 | 81.041 s / 39,027,156 字节 |
| 平均码率 | 3,852,583 bps（约 3853 kbps） |
| 分辨率 / 帧率 | 1280×720 逐行，平均约 25.02 fps（`avg_frame_rate` ≈ 25.03；容器 `r_frame_rate` 为 50/1，属误导性标记，见下） |
| 编码 | H.264 Constrained Baseline，level 3.1，无 B 帧 |
| 帧大小 | 全部 2028 帧：最小 266、中位 15844、P99 79734、最大 123670 字节；P 帧中位约 15.8 KB；I 帧明显分成约 7 KB 与约 62–70 KB 两簇 |
| 采集命令 | `libx264`、`veryfast`、`tune zerolatency`、`baseline`、`-g 25`，仅 `-r 25`，**没有** `-b:v` / `-crf`（即默认 CRF 23），未强制缩放，分辨率跟摄像头 |

约 3.85 Mbps 的 720p@25 对默认 CRF 23 属于中等码率，远低于本机 TCP 承载能力。该次会话「点播成功」，约 81 秒后因无人观看结束，设备侧没有发送刷屏，不能说明码流把链路撑满。由 1 ms 时间戳间隔反推的「瞬间码率」是分片被拆成多帧后的计算假象，不能用来作为降码率的依据。本次**没有修改编码参数**。

### 根因

`internal/videosrc.AnnexBSplitter.feed` 在当前访问单元已有一个 VCL 之后，把后续每一个 VCL NAL 都当成新画面的开始。`libx264 -tune zerolatency` 会打开 `sliced-threads`，同一幅画面常被切成多个 slice（本次 I 帧对应的宏块划分约为 `first_mb_in_slice` 0 与 320）。这些 slice 被当成独立访问单元，带上各自的 `time.Now()` 时间戳，再分别打成 PS/PES 送出。解码端拿到的是不完整画面，只能做错误隐藏，看起来像马赛克。

这是访问单元边界判断错误，不是量化块效应，也不是随机丢包。

### 证据

用 ffmpeg 对上述录像做独立解码（修复前样本）：

- 172 条 I 帧 concealment：86 次缺 3280 个宏块，86 次缺 320 个宏块；
- 1280×720 = 80×45 = 3600 个宏块，3280+320=3600；171 组相邻记录都能凑成完整一帧；
- 104 次 `corrupt decoded frame`，以及大量非单调 DTS；
- 录像开头两个 I 样本仅相隔 1 ms，大小 7013 + 61461 = 68474 字节，比例约 10.2% / 89.8%，与 320/3600、3280/3600 接近。

**用户于 2026-11-24 06:44 确认「厉害，好了。」作为画面验收。** 替换修复版之后，**没有再次录取点播录像并用 ffmpeg 做独立解码复测**；解码侧「不再出现成对的 3280+320 concealment」这一项仍待补测。本次也没有代替用户观看 WVP 窗口，画面结论以用户确认为准。

### 代码改动

- `internal/videosrc/annexb.go`
  - `feed`：仅当新的 VCL 的 `first_mb_in_slice == 0`，或该字段无法解析时，才开启新的访问单元；`first_mb_in_slice != 0` 的 slice 留在当前画面。
  - 新增 `firstMbInSlice` / `decodeUE` / `getBit`，按 H.264 基准档在 1 字节 NAL 头之后读取无符号指数哥伦布码。
- `internal/videosrc/annexb_test.go`：UE 往返、`first_mb` 解析、同一 IDR/P 画面的两片应合成一个 AU、下一画面以 `first_mb=0` 开始。原有 SPS/PPS/IDR、AUD、SEI、分片推送等测试保留。

### 机制

一个访问单元应包含同一幅编码画面的全部 VCL slice（以及其前的 SPS/PPS/SEI/AUD）。按 `first_mb_in_slice` 聚合后，PS 复用与平台解码器一次看到完整画面，无需改码率或分辨率。

## 5. 现场配置：WVP 与 ZLMediaKit 的 mediaServerId（非本仓库改动）

点播从「完全无画」到「能看见」（随后才进入第 4 节的马赛克问题），关键一步是现场把两侧媒体服务器标识对齐。**这不是本仓库的源代码修改，也不提交任何平台配置文件或密钥。**

脱敏说明：

- WVP 配置中的媒体服务器 id（`media.id`）为 `local-zlm`；
- 当时正在运行的 ZLMediaKit 配置里，`[general] mediaServerId` 仍是发行默认值 `your_server_id`；
- `on_publish` 回调携带 `your_server_id`，WVP 日志出现「找不到对应的mediaServer」，拒绝推流并关闭 TCP 收流端口；
- 设备侧先表现为 TCP 被对端关闭（第 3 节的刷屏或后来的单次永久失败 WARN）。

处理：备份 ZLM `config.ini`（完整字节副本，保留编码与换行），**只改这一处** `mediaServerId=local-zlm`，按原实例方式重启媒体服务，不改 WVP 侧标识，不改其他字段。重启后 WVP 记录到 `[ZLM HOOK] zlm 启动 local-zlm`，此前周期性「心跳超时但探测仍在线」不再出现。2026-11-24 06:15:22 的点播中，WVP 已「推流鉴权-允许」并「点播成功」。

回滚方法：用当地时间命名的 `config.ini` 备份覆盖回去，再只重启该 MediaServer 实例。备份与配置原文保留在本机，不进本仓库。
